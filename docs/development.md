# 开发与版本管理

[返回首页](../README.md) · [版本记录](changelog.md)

## 分支与PR

- `main` 是生产分支，只接收经过检查的PR，不直接在其上开发、提交、推送或强推。
- 每项改动单独使用 `feat/描述`、`fix/描述`、`docs/描述`、`chore/描述` 或 `release/x.y.z`。不要求维护长期 `develop` 分支。
- 功能、修复、文档、依赖及版本号调整都通过PR；版本声明和对应功能或修复放在同一个PR。
- 开始前检查工作区和分支，保留已有改动。新分支通常基于最新 `origin/main`；已有未推送提交不得用reset或强推清除，应保留到待审PR中。

```bash
git fetch origin
git switch -c feat/short-description origin/main
```

提交采用中文Conventional Commits，例如 `feat: 增加图文导出`、`fix: 修复大图切换`。完成本地检查后，取得明确授权再推送分支、创建以 `main` 为目标的PR。PR中说明范围、版本、验证和兼容影响；合并以Squash为默认，标题作为中文提交摘要。

## 版本规则

| 级别 | 用途 | 示例 |
| --- | --- | --- |
| major | 不兼容改动，必须说明迁移和回退 | `1.x.x` → `2.0.0` |
| minor | 新增一组功能或显著增强 | `0.2.x` → `0.3.0` |
| patch | 兼容的bugfix、稳定性或安全修复 | `0.2.0` → `0.2.1` |

`0.x`阶段不兼容改动也须在PR和版本记录中明确标注，不能伪装成patch。只改文档或开发流程不强制升版，先记录在“未发布”，随下次版本归档。

同一未发布功能版本内的补充和完善归入该版本，不因新增单个字段或界面细节机械升版；是否开启下一minor按整体功能范围与发布计划确定。

应用版本统一维护 `pixi.toml`、根目录和两个前端的 `package.json`、根目录及公开前端的npm锁文件。数据包和图文清单的格式版本独立维护，不机械跟随应用版本。

README固定显示两项：

- 最新版本：实际最新应用版本，如 `v0.2.3`。
- 当前功能版本：该major/minor的功能起点，如 `v0.2.0`，下面保留这一版本的主要feature。

发布patch只更新“最新版本”及必要升级提示，不能用bugfix列表覆盖 `v0.2.0` 的feature。到 `v0.3.0` 或下一major时才更新功能摘要；此前特性和每次修复完整保存在 `docs/changelog.md`，按新到旧排列。根 `CHANGELOG.md` 仅作兼容入口。

## 合并检查

1. 运行 `pixi run test`，确认版本一致性、两端测试和构建、公开产物审计通过。涉及大图、布局或交互时另跑隔离Playwright回归。
2. 核对README、版本记录和配置/迁移说明；PR模板逐项确认。只暂存本次文件，不包含私密配置、原图、数据库、图文内容、缓存或真实导出。
3. PR的 `Checks` 工作流 `test` 检查必须通过。检查只使用合成fixture，不下载个人数据，不构建带个人内容的网站，也不部署。
4. 检查通过并获得合并授权后才合入 `main`。单人仓库也保留PR记录，不要求作者自审批准；多人协作可要求独立review。

要在GitHub服务端强制执行，须另行启用 `main` 分支保护或Ruleset：要求PR及检查通过、禁止强推和删除，并核对管理员绕过权限。文档和PR模板不能代替服务端保护；提交或合并本规范不自动修改GitHub设置。

## 发布边界

- 合并不等于发布。软件标签 `vX.Y.Z` 和软件Release只能在单独授权后指向已合入、验收通过的 `main` 提交；记录实际标签、提交和发布日期。
- 照片数据使用独立的 `data-*` Release，与软件版本无关。附件上传前须人工确认公开内容。
- PR测试、代码推送和版本号变更均不触发Pages；部署仍只由手动 `workflow_dispatch` 指定数据版本执行。
- 上传、创建或合并PR、打标签和部署分别需要明确授权。不要把“本地开发完成”写成“已上线”。
